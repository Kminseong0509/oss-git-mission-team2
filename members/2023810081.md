\## 6. 내가 겪은 오류 또는 어려웠던 점



\### 1. README.md 관련 PR 충돌



README.md를 수정하는 PR이 여러 개 있었기 때문에, 한 PR을 먼저 merge한 뒤 다른 README PR에서 conflict가 발생했다.



\### 2. docs/conflict-log.md 중복 PR



docs/conflict-log.md를 수정하는 PR이 여러 개 있었고, 일부 내용이 중복되어 있었다.

따라서 더 전체적인 내용을 담고 있는 PR을 기준으로 merge하고, 중복되는 PR은 닫는 방식으로 정리했다.



\### 3. 삭제/수정 충돌 실습



3주차에서 한 branch는 `docs/notice.md` 파일을 삭제하고, 다른 branch는 같은 파일을 수정하는 상황을 만들었다.

이 과정에서 Git이 파일을 삭제할지 유지할지 자동으로 판단하지 못하는 modify/delete conflict 상황을 확인했다.



\---



\## 7. 해결 방법



\* PR의 `Files changed` 탭에서 실제 수정된 파일을 확인했다.

\* 같은 파일을 수정한 PR이 여러 개 있으면 중복 여부를 먼저 확인했다.

\* conflict가 발생한 PR은 바로 merge하지 않고 작성자에게 conflict 해결을 요청했다.

\* 중복되는 PR은 merge하지 않고 close했다.

\* merge 가능한 PR은 `Ready to merge` 상태를 확인한 뒤 main branch에 merge했다.

## 9. 이번 미션에서 배운 점



GitHub 협업에서는 main branch에 직접 작업하지 않고, branch를 만들어 작업한 뒤 Pull Request로 검토받는 과정이 중요하다는 것을 배웠다.



또한 PR을 merge하기 전에는 단순히 Ready to merge 상태만 보는 것이 아니라, 어떤 파일이 수정되었는지, 과제 기준에 맞는지, 불필요한 변경이 포함되지 않았는지 확인해야 한다는 것을 알게 되었다.



conflict는 Git의 오류라기보다 여러 사람이 같은 파일을 수정하는 과정에서 사람이 최종 내용을 선택해야 하는 상황이라는 점을 이해했다.

## 10. 6월 시험 대비로 기억할 점



* main branch에서 직접 작업하지 않는다.

* 작업 전에는 `git pull origin main --no-rebase`로 최신 상태를 가져온다.

* 새 작업은 branch를 만들어 진행한다.

* `git status`로 현재 상태를 자주 확인한다.

* push가 rejected 되면 원격 저장소가 더 최신일 수 있으므로 pull 후 다시 push한다.

* conflict marker인 `<<<<<<<`, `=======`, `>>>>>>>`는 최종 파일에 남기면 안 된다.

* PR을 merge하기 전에는 `Files changed`에서 실제 수정 내용을 확인해야 한다.

* 같은 파일을 여러 PR이 수정하면 한 PR을 merge한 뒤 다른 PR에서 conflict가 발생할 수 있다.
